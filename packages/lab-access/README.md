# @precisa-saude/fhir-lab-access

Cliente do lado do receptor para o protocolo Open Labs Brasil: o backend de um aplicativo voltado ao paciente acessa catálogo, unidades, agenda, agendamento e resultados de um laboratório, com o consentimento que o paciente dá na página do próprio laboratório.

## Situação

> **Rascunho. Não use em produção.**
>
> - Implementa a versão **0.2.2** de uma especificação que **ainda não foi publicada**, versão de protocolo `0.2`. Enquanto a versão começar com 0, qualquer mudança da especificação pode quebrar este pacote.
> - **Nunca foi testado contra um laboratório real.** Todos os testes rodam contra um provedor simulado em memória, escrito a partir do texto da especificação.
> - O pacote é **privado** (`"private": true`) e não está no npm. Ele só será publicado depois que a especificação for aberta.
> - Os perfis FHIR que o protocolo referencia ainda estão sendo escritos. Os tipos locais deste pacote cobrem só os elementos que o cliente lê.

---

## Instalação

O pacote não está publicado. Dentro deste monorepo, ele entra como dependência de workspace:

```json
{
  "dependencies": {
    "@precisa-saude/fhir-lab-access": "workspace:^"
  }
}
```

Requer Node.js 22.12 ou superior. O pacote tem uma dependência externa de runtime, [`jose`](https://github.com/panva/jose), usada para assinar a asserção do cliente, verificar a assinatura do registro e calcular thumbprints de chave. A `jose` 6 é distribuída só como módulo ES: a saída CommonJS deste pacote depende de o Node carregar módulos ES com `require`, o que vale a partir da versão 22.12.

## O que o receptor precisa ter

1. Uma entrada ativa no registro de participantes, com `client_id`, `redirect_uris` e certificado de transporte.
2. Um par de chaves RSA de assinatura (2048 bits ou mais), com a chave pública no `jwks_uri` informado no registro.
3. Um certificado de cliente TLS, com chave distinta da chave de assinatura.
4. O conjunto de chaves inicial do registro, recebido na admissão.

Chaves privadas e refresh tokens ficam só no backend. Este pacote não roda em navegador nem em aplicativo móvel.

## Uso rápido

### Verificar o registro e criar o cliente

```ts
import { readFileSync } from 'node:fs';
import { createPrivateKey } from 'node:crypto';
import {
  createMtlsTransport,
  LabAccessClient,
  verifyRegistry,
} from '@precisa-saude/fhir-lab-access';

// Bytes exatos dos dois arquivos, como baixados. A busca é do aplicativo:
// o endereço de publicação do registro ainda não foi definido.
const { registry } = await verifyRegistry({
  registry: readFileSync('participantes.json'),
  signature: readFileSync('participantes.json.jws', 'utf-8'),
  // Primeiro documento: conjunto de chaves inicial recebido na admissão e o
  // ambiente em que o receptor opera. Nos seguintes: { current: registroAnterior }.
  trust: { environment: 'pilot', initialKeys },
});

const client = new LabAccessClient({
  clientId: 'c2b8f6a4-71de-4c0b-8f3a-9e5d2a7b6c31',
  registry,
  signingKey: {
    key: createPrivateKey(readFileSync('assinatura.key.pem')),
    kid: 'kid-publicado-no-jwks-uri',
  },
  transport: createMtlsTransport({
    cert: readFileSync('transporte.crt.pem'),
    key: readFileSync('transporte.key.pem'),
  }),
  // Onde ficam as revogações pendentes. Use um armazenamento durável.
  revocationStore: armazenamentoDeRevogacoes,
});
```

`verifyRegistry` é o único caminho para obter um registro: não existe carga sem conferência de assinatura. Quando chegar um documento novo, verifique com `trust: { current: client.registry }` e entregue o resultado a `client.updateRegistry(...)`.

`client.providers()` lista só os provedores que podem ser oferecidos ao paciente: ativos no registro e com versão de protocolo efetiva com este receptor.


### Jornada de consentimento

```ts
// 1. Criar o consentimento. A criação não identifica o paciente: o CPF do
// paciente no aplicativo só é conferido, e com CPF inválido a jornada não começa.
const consent = await lab.createConsent(
  {
    expirationDateTime: '2027-05-15T03:00:00Z',
    purpose: 'Guardar os resultados dos seus exames no seu histórico pessoal.',
    scopes: ['appointment.write', 'results.read', 'consent.read'],
  },
  { expectedCpf: cpfDoPacienteNoAplicativo },
);

// 2. Abrir a jornada: PAR com PKCE e state. O CPF é conferido de novo e não
// entra na jornada.
const journey = await lab.startAuthorization({
  consent,
  expectedCpf: cpfDoPacienteNoAplicativo,
  redirectUri: 'https://app-paciente.example/conexoes/retorno',
});
// Guarde `journey` no backend, ligado à sessão do paciente.
// Abra `journey.authorizationUrl` no navegador do sistema, nunca em WebView.

// 3. No retorno ao redirect_uri: conferir, trocar o código e conferir o titular.
// PatientMismatchError vem de '@precisa-saude/fhir-lab-access'.
try {
  const access = await lab.completeAuthorization({
    callback: urlDeRetornoCompleta,
    expectedCpf: cpfDoPacienteNoAplicativo,
    journey,
    onTokensUpdated: (state) => guardarCifrado(state),
  });
  guardarCifrado(access.exportState());
} catch (error) {
  if (error instanceof PatientMismatchError) {
    // A conta usada no laboratório é de outra pessoa. Os tokens foram
    // descartados e o consentimento revogado. Se `error.revocation` for
    // "pending", a revogação ficou pendente (ver "Revogação pendente").
  }
  throw error;
}
```

`completeAuthorization` só devolve o acesso depois de ler o consentimento com o token de paciente e comparar o CPF devolvido pelo laboratório com `expectedCpf`. O CPF recebido não aparece em nenhum retorno, erro ou evento. Quando a conferência não pode ser feita (a leitura falha, ou vem sem CPF de 11 dígitos com dígitos verificadores válidos), o vínculo não é concluído e a revogação usa `RECEIVER_TERMINATION`, nunca `PATIENT_MISMATCH`: o erro é `HolderVerificationError`.

### Resultados e agendamento (com paciente)

```ts
const access = lab.resumePatientAccess(estadoGuardado, {
  onTokensUpdated: (state) => guardarCifrado(state),
});

const laudos = await access.searchDiagnosticReports({
  lastUpdatedAfter: ultimaSincronizacao,
});
// laudos.resources: DiagnosticReport. laudos.included: Observation.

// O aplicativo monta o Appointment, com os pedidos de exame em `contained`.
const criado = await access.createAppointment(appointment);
// Repetir a mesma chamada depois de uma falha de rede não duplica o agendamento.

// Link de pagamento, se houver: abra no navegador do sistema, sem alterar.
const pagamento = readPaymentLink(criado.resource);

const lido = await access.readAppointment(criado.resource.id);
await access.rescheduleAppointment({
  current: lido.resource,
  end: '2026-11-24T09:15:00-03:00',
  etag: lido.etag,
  slot: 'horario-24nov-09h',
  start: '2026-11-24T09:00:00-03:00',
});

// Revogar quando o paciente pedir. Os tokens são descartados antes da chamada.
await access.revoke();
```

> **Nota:** o cliente cuida do transporte (mTLS, tokens, cabeçalhos, repetição e os endpoints do protocolo) e não monta nem ajusta conteúdo clínico. `createAppointment` envia o `Appointment` como recebido, depois de conferir as regras estruturais que o protocolo e o perfil `br-lab-appointment` exigem do receptor: participantes paciente e unidade distinguidos por `actor.type`, paciente só pela referência `Patient/{fhir_id}`, sem `identifier`, e `subject` de cada pedido contido igual a ela, pedidos `active` e `order` com ao menos um `coding`, um `basedOn` local por pedido, identificador do receptor no conjunto de caracteres do protocolo e nenhuma extensão de link de pagamento. Copiar para cada pedido os `coding` do item do catálogo é do aplicativo. Na remarcação e no cancelamento, troca só `slot`, `start`, `end`, `status` e `cancelationReason`, e devolve o resto como foi lido. `readPaymentLink` lê o link só da extensão `https://fhir-brasil.dev.br/ig/StructureDefinition/payment-link`, em `valueUrl` e com `https`. Sem a extensão, devolve `undefined`. Com a extensão repetida, ou sem URL `https`, lança `LabAccessProtocolError` e não devolve link nenhum. O domínio não é conferido, porque o registro não lista os domínios do provedor. O aplicativo abre o link no navegador do sistema, sem alterar a URL.

### Revogação pendente

Toda revogação enviada pelo receptor (pedido do paciente, encerramento do vínculo, `PATIENT_MISMATCH` ou conferência impossível) é gravada no `revocationStore` no momento em que é decidida, antes da primeira chamada: um reinício no meio das tentativas não a perde. Depois vêm no máximo três tentativas automáticas ao todo, contando o pedido do token de provedor, com recuo e `Retry-After`. Falha que não admite repetição (`invalid_client`, outro 4xx, um 404 sem o código `CONSENT_NOT_FOUND`) e espera de `Retry-After` acima de `retry.maxDelayMs` encerram as tentativas na hora. 404 `CONSENT_NOT_FOUND` e 422 `CONSENT_INVALID_STATE` contam como revogação concluída. Sem confirmação, a revogação gravada fica pendente, e o erro (`RevocationPendingError`, ou `revocation: 'pending'` nos erros da conferência do titular) traz a pendência.

O provedor não é chamado, nem para revogar, quando ele ou o receptor não estão `active` no registro em uso, quando não há versão efetiva entre os dois ou quando o registro expirou há mais de 7 dias. A pendência fica à vista do paciente e é tentada assim que a condição acaba.

O pacote é uma biblioteca e não roda temporizador. O aplicativo chama `retryPendingRevocations()` do próprio agendador, com a frequência que quiser (a cada poucos minutos, por exemplo), e também depois de reiniciar: as revogações gravadas e não confirmadas entram no calendário. Cada pendência guarda em `nextAttemptAt` o próximo vencimento, de hora em hora nas primeiras 24 horas e uma vez por dia depois, nunca antes do instante de um `Retry-After` recebido (`notBefore`), e cada vencimento faz uma única chamada. A pendência termina quando o provedor confirma ou quando passa a expiração do consentimento, nunca por desistência.

```ts
// No agendador do aplicativo.
for (const resultado of await client.retryPendingRevocations()) {
  registrarNaAuditoria(resultado.consentId, resultado.outcome);
}

// Na tela de consentimentos do paciente.
for (const pendente of await client.pendingRevocations()) {
  // "O aplicativo já parou de acessar seus dados. O laboratório ainda não
  // confirmou a revogação. Você pode revogar direto em:"
  mostrar(pendente.consentId, pendente.consentManagementUri);
}
```

`InMemoryRevocationStore`, o padrão, não é durável. A especificação exige que a pendência sobreviva a reinício do backend: em produção, implemente `RevocationStore` (`list`, `save`, `remove`) sobre o banco do aplicativo.

## Propriedades de segurança

- **Nenhuma credencial de paciente.** O pacote não aceita, não guarda e não transmite senha do laboratório, código de uso único, cookie de sessão nem qualquer outra credencial do paciente. Não existe função, opção ou campo para isso. O paciente se autentica só na página do laboratório, aberta no navegador do sistema.
- **mTLS em toda chamada entre servidores.** O transporte padrão apresenta o certificado de cliente, exige TLS 1.2 ou superior, oferece no TLS 1.2 só as quatro suítes que o protocolo admite e sempre confere o certificado do servidor. Não há opção para desligar a conferência.
- **Cliente autenticado por `private_key_jwt`.** Asserção assinada com PS256, com o `issuer` do laboratório como `aud` em texto simples, `jti` novo a cada chamada e validade de 60 segundos.
- **Autorização só por PAR, com PKCE `S256` e `state`.** A URL aberta no navegador leva apenas `client_id` e `request_uri`.
- **Retorno conferido antes da troca do código.** `iss` idêntico ao `issuer` do laboratório da jornada, também nas respostas de erro, e `state` igual ao enviado.
- **Conferência do titular.** A primeira chamada depois dos tokens é a leitura do consentimento. Com CPF divergente, o consentimento é revogado com `PATIENT_MISMATCH`, os tokens são descartados e nenhuma chamada à API FHIR acontece.
- **Endereços só do registro e dos metadados.** O `issuer` vem do registro assinado, os endpoints OAuth vêm do documento de metadados desse `issuer`, e o link de próxima página só é seguido com o mesmo esquema, host e porta do `fhir_base_url` do registro e caminho dentro do caminho da base. Redirecionamento HTTP nunca é seguido.
- **Metadados conferidos campo a campo.** O provedor é recusado se faltar, ou divergir, qualquer valor obrigatório da tabela de metadados da especificação, inclusive `jwks_uri` e os escopos do registro em `scopes_supported`.
- **Token de provedor por escopo.** Um token para cada escopo, e `consent.manage` sempre sozinho. Nenhum token de acesso é usado depois de `expires_in`, com margem de 60 segundos. A revogação de token do RFC 7009 nunca é chamada: encerrar o acesso é sempre revogar o consentimento.
- **Registro expirado.** Nos 7 dias depois de `expires_at`, o cliente não abre jornadas, não cria consentimentos e não pede tokens de catálogo, unidades ou agenda, mas segue lendo e revogando consentimentos com token só de `consent.manage`. Depois disso não pede token nenhum, e as revogações ficam pendentes.
- **Token só no cabeçalho `Authorization`.** Nunca na URL.
- **Erros e eventos sem dado pessoal.** Mensagens de erro e eventos de `onInteraction` não carregam token nem CPF.

O que fica com o aplicativo: guardar refresh tokens cifrados em repouso, manter chaves privadas no backend, abrir a autorização e o link de pagamento no navegador do sistema, buscar o registro por HTTPS ao menos a cada 60 minutos, consultar o estado de cada consentimento autorizado ao menos a cada 24 horas, oferecer ao paciente a tela de consentimentos com as revogações pendentes e a página do provedor, guardar as pendências em armazenamento durável, chamar `retryPendingRevocations` de um agendador e não gravar CPF em log.

## API

### `verifyRegistry(input)`

Verifica um candidato a registro pela lista de passos V2 a V14 da seção 8.3, na ordem: formato do JWS de conteúdo destacado, algoritmo PS256 sem `crit`, chave pelo `kid` (nenhum outro membro do cabeçalho serve para obter a chave, e `typ` e membros a mais são ignorados), `kid` igual ao thumbprint e chave RSA de 2048 bits ou mais, assinatura sobre os bytes recebidos, schema (inclusive a regra de uma única versão `0.x` em `protocol_versions`), ambiente, `sequence`, `issued_at`, validade de até 30 dias, `expires_at`, `kid` das chaves anunciadas e unicidade dos participantes. Fora desses passos não há regra de recusa. V1, baixar os dois arquivos por HTTPS, é do aplicativo. Devolve `{ registry, changed }` ou lança `RegistryVerificationError` com o motivo em `reason` e o passo em `step`.

### Erros

Todos estendem `LabAccessError`, que traz `retry` (o que precisa acontecer para repetir) e `retryable`.

| Classe                                              | Quando                                                                                     |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `RegistryVerificationError`                         | Candidato a registro recusado                                                              |
| `RegistryExpiredError`                              | O registro em uso expirou e a operação está suspensa                                       |
| `ProviderUnavailableError`, `ReceiverStatusError`   | Provedor ausente, inativo ou sem versão efetiva que o pacote implemente. Receptor inativo  |
| `ProviderMetadataError`, `IssuerMismatchError`      | Metadados fora do perfil. `issuer` diferente do esperado                                   |
| `OAuthError`                                        | Erro JSON do PAR ou do endpoint de token (`invalid_client`, `invalid_grant`, ...)          |
| `StateMismatchError`, `AuthorizationResponseError`  | Retorno da autorização recusado                                                            |
| `AuthorizationDeniedError`                          | O laboratório devolveu `error` no retorno (`access_denied`, ...)                           |
| `PatientMismatchError`, `HolderVerificationError`   | Titular divergente, ou conferência do titular impossível                                   |
| `ConsentEndedError`, `RefreshTokenRevokedError`     | O consentimento saiu de `AUTHORISED`, ou o refresh token foi revogado isoladamente         |
| `RevocationPendingError`, `TokensDiscardedError`    | Revogação não confirmada e gravada como pendente (`pending`). Acesso já descartado         |
| `LabAccessAuthorizationError`                       | Token, certificado, escopo (seção 6.3.1 da especificação)                                  |
| `LabAccessRequestError`                             | Requisição malformada, recurso inexistente (6.3.2)                                         |
| `LabAccessConsentError`                             | Regras do consentimento (6.3.3)                                                            |
| `LabAccessSchedulingError`                          | Agenda e agendamento: `SLOT_UNAVAILABLE`, `VERSION_CONFLICT`, ... (6.3.4)                  |
| `LabAccessOperationalError`                         | `RATE_LIMITED`, `INTERNAL_ERROR`, `PROVIDER_UNAVAILABLE`, `UPSTREAM_TIMEOUT` (6.3.5)       |
| `LabAccessApiError`                                 | Base das cinco anteriores. Também usada para código desconhecido, tratado pelo status HTTP |
| `LabAccessTransportError`, `LabAccessProtocolError` | Falha de rede ou TLS. Resposta fora do formato do protocolo                                |
| `LabAccessConfigError`, `ScopeError`                | Argumento ou configuração inválida. Escopo que a chamada não pode usar                     |

Os erros com `OperationOutcome` trazem `status`, `code` (o código do protocolo), `issueCode`, `operationOutcome`, `interactionId` e `retryAfterSeconds`.

Repetição automática: leituras, criação condicional de agendamento e `PUT` com `If-Match` são repetidos em `429` e `503` (esperando o `Retry-After`) e em `500`, `504` e falha de rede (recuo a partir de 1 segundo, dobrando), até 3 tentativas. Erros 4xx não são repetidos. A criação de consentimento e a troca do código de autorização nunca são repetidas sozinhas. A revogação de consentimento conta as 3 tentativas incluindo o pedido do token de provedor e, sem confirmação, passa a pendente.

### Tipos FHIR

`DiagnosticReport`, `Observation`, `Patient` e `Consent` usam os tipos de `@precisa-saude/fhir`. Os recursos abaixo ainda não existem no core e têm tipos mínimos locais, que deveriam migrar para lá:

- `FHIRAppointment`, `FHIRServiceRequest`, `FHIRSlot`, `FHIRSchedule`
- `FHIRLocation`, `FHIRHealthcareService`
- `FHIRActivityDefinition`, `FHIRChargeItemDefinition`
- `FHIROperationOutcome`, `FHIROperationOutcomeIssue` (hoje duplicados no `fhir-rnds`)
- `FHIRSearchBundle`, `FHIRSearchBundleEntry`, `FHIRBundleLink`, `FHIRCapabilityStatement`

## Conformidade

A tabela liga cada requisito do receptor, e os de registro que valem para o receptor, do capítulo de conformidade da especificação 0.2.2 aos testes deste pacote. Um teste em `src/__tests__/conformance.test.ts` confere que a tabela e os nomes dos testes batem.

Situações:

- **Coberto**: o comportamento inteiro é do pacote e tem teste.
- **Parcial**: o pacote garante uma parte, testada, e o resto depende do aplicativo.
- **Fora do alcance**: o requisito fala de telas, do aplicativo móvel ou de armazenamento. Uma biblioteca de backend não tem como prová-lo.
- **Retirado**: o requisito foi retirado da especificação e fica na tabela só para registro.

Nenhum destes testes roda contra um laboratório real.
